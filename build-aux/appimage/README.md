# AppImage packaging

This directory holds everything specific to the official AppImage of
Linux Image Writer (`io.github.pc_freedom.linux-image-writer`). It is a
packaging layer only: the application, its Safety Engine and the Flatpak
build are not changed for it.

> **Status:** ready for release. `build.sh` builds a complete AppDir -- the
> binary, the app's own files, the libraries linuxdeploy collects, GTK's
> runtime resources and `AppRun` -- checked and listed in a bundle manifest,
> and packs it reproducibly into an AppImage (`out/dist/`, with its SHA-256),
> which runs through FUSE and with `--appimage-extract-and-run`; tested on
> Ubuntu 24.04, Debian 13, Fedora 44 and openSUSE Tumbleweed (X11 and
> Wayland). Builds made here directly are **test builds**
> (`…-test-x86_64.AppImage`); official release artifacts are built only by
> `build-aux/release/release.sh` (its README), and users' instructions are
> in `docs/AppImage.md`.

## Purpose

To offer a single-file download that runs on current Linux distributions
without installation, alongside the Flatpak, while keeping the same safety
guarantees: the AppImage is the same GUI binary, built from the same source,
talking to the same host services.

## Principles

### The application is not changed for packaging

- The Rust code under `src/` is not modified to make the AppImage work. If a
  change ever turns out to be unavoidable, it is proposed and reviewed on its
  own, not folded into packaging work.
- `build-aux/flatpak/` is not modified for the AppImage.
- The existing files in `data/` (desktop entry, MetaInfo, icon) and `po/`
  (translations) are the source of truth. The AppImage build installs them
  from there, as the Flatpak manifest does; no AppImage-specific copies are
  kept in the repository.
  - Translations are found without any code change: the GUI looks for them
    in `share/locale` next to its own `bin/` directory
    (`src/bin/linux-image-writer/i18n.rs`), which is `usr/share/locale`
    inside the AppDir.

### Packaging lives in this directory

Everything AppImage-specific is in `build-aux/appimage/`. The only change
planned outside it is ignoring the build output in `.gitignore` (and, later,
a CI workflow that calls the script here). The licence document of the Rust
crates is not AppImage-specific: it is generated by
`build-aux/rust-licenses/`, shared with other packagings (see "Licences").

### Fixed build environment: Ubuntu 24.04 LTS

The AppImage is never built on a developer's host. It is built in the
container defined by `Containerfile`:

- Base image `ubuntu:24.04`, pinned to its index digest
- GTK 4 and libadwaita from Ubuntu 24.04 (GTK 4.14, libadwaita 1.5), which
  meet the GUI's requirements (GTK 4.12+, libadwaita 1.5+)
- Every Ubuntu package from one point in time of the Ubuntu Snapshot Service
  (see below), not from the live archive
- Rust from rustup, at the version `rust-toolchain.toml` names; Ubuntu's
  `rustc` is never used. `rustup-init` is pinned by version and SHA-256.

### Pinned inputs

The build environment is determined by these inputs, each pinned on its own
and each changed only on purpose:

| Input | Where | Current value |
|---|---|---|
| Ubuntu base image | `Containerfile`, `UBUNTU_IMAGE` | `ubuntu:24.04@sha256:a853f94d…1b60` (multi-arch index digest) |
| Ubuntu Snapshot ID | `Containerfile`, `UBUNTU_SNAPSHOT` | `20261002T130000Z` |
| rustup-init | `Containerfile`, `RUSTUP_VERSION` and `RUSTUP_INIT_SHA256` | 1.29.1 |
| Rust toolchain | `rust-toolchain.toml` (repository root) | 1.98.1 |
| Rust crates | `Cargo.lock` (built with `--locked`) | — |
| cargo-about | `build-aux/rust-licenses/cargo-about.lock` (installed by the `Containerfile`; archive and executable checked by SHA-256) | 0.9.2 |

The AppImage tools to come (`linuxdeploy`, `appimagetool` and the type 2
runtime) will be pinned the same way, by version and SHA-256.

The built image records the first three as labels:

```sh
podman image inspect linux-image-writer-appimage-build \
  --format '{{json .Labels}}'
```

### The Ubuntu snapshot

**Why it is pinned.** The AppImage bundles GTK 4, libadwaita, GLib and the
libraries under them, all taken from the Ubuntu packages installed in the
build image. Pinning only the base image is not enough: `apt-get` would
install whatever the live archive holds on the day of the build, so two
builds of the same commit could bundle different libraries. With the
snapshot pinned, the package set is the same whenever the image is built.

**How it works.** apt's own snapshot support (`APT::Snapshot`, the same as
`apt-get update --snapshot`) fetches the archive as it was at that time from
`snapshot.ubuntu.com`. The base image has no CA certificates, so the
`ca-certificates` package is installed first, from the same snapshot, with TLS
peer verification turned off for `snapshot.ubuntu.com` in that one step only.
This does not weaken what is installed: apt still checks the archive's
signature against the Ubuntu keyring in the base image, and every package's
hash. Every later download verifies TLS as usual.

**It is not pinned forever.** Pinning is for reproducibility, not for
keeping old libraries. Security fixes in GTK, GLib and the rest only reach
the AppImage when the snapshot moves forward, so the snapshot is updated
deliberately -- for every release, and whenever a relevant security update
appears -- through this sequence:

1. Choose a new snapshot ID (`YYYYMMDDTHHMMSSZ`, UTC) and check it exists:
   `https://snapshot.ubuntu.com/ubuntu/<ID>/dists/noble-updates/InRelease`
   must be served. The `Date:` lines of the `noble-updates` and
   `noble-security` InRelease files show which archive state it contains.
2. Set `UBUNTU_SNAPSHOT` in `Containerfile` to it.
3. Rebuild the image without the cache
   (`podman build --no-cache ...`), then build and run all tests in it.
4. Compare the new bundle manifest (the list of bundled libraries the
   AppImage build will produce) with the previous release's, and review
   every library whose version changed.
5. Test the AppImage, then release it, noting the snapshot ID in the release
   notes.

The same applies to the base image digest, which is updated together with
the snapshot when a newer `ubuntu:24.04` image is published.

### glibc 2.39 is the minimum

Binaries built against Ubuntu 24.04 require glibc 2.39 or later. The AppImage
therefore supports distributions with glibc 2.39 or later (for example
Ubuntu 24.04 and later, Debian 13, Fedora 40 and later). Older ones (Ubuntu
22.04, Debian 12, RHEL 9 and its rebuilds) are not supported; for them, the
Flatpak is the way to run the app.

### What is bundled, and what is not

Bundled: GTK 4, libadwaita, GLib / GIO / GObject, Pango and the other
user-space libraries GTK needs, plus the runtime resources GTK expects to find
(its GSettings schemas, and the icons the GUI uses).

Never bundled, always taken from the host:

- glibc and the dynamic loader (`libc.so.6`, `ld-linux-x86-64.so.2`, and the
  rest of glibc)
- GPU drivers: Mesa, vendor drivers, and the GL / EGL / GBM / DRM libraries
  that must match them
- The kernel, the D-Bus daemons, polkit, and the UDisks2 daemon

Devices are reached exactly as in every other build: through the host's
UDisks2 over the D-Bus system bus (`OpenDevice`, `Unmount`, `PowerOff`), with
the host's polkit deciding on authorization.

Every file that ends up in the AppImage is listed in the bundle manifest
(`out/bundle-manifest.txt`), each library with its Ubuntu package and
version, and the build fails if anything from the never-bundled list is found
(see "Checks on the bundle" below).

#### Measured: what is bundled (Ubuntu 24.04, GTK 4.14, libadwaita 1.5)

85 shared libraries (about 88 MB, from 79 Ubuntu packages), the gdk-pixbuf
SVG loader and librsvg among them. Besides GTK, libadwaita, GLib, Pango, cairo and their image and text
libraries, libadwaita 1.5's link to `libappstream` brings in curl, GnuTLS,
OpenSSL's libcrypto, Kerberos, OpenLDAP, libssh and ICU; the app never uses
them for networking, but they are bundled because they are linked.

No GL, EGL, GBM or DRM library is linked at all: GTK loads them from the
host through libepoxy at run time.

#### The libraries the host provides

Exactly the 17 SONAMEs in `host-libs.txt`; the build fails if anything else
resolves outside the AppDir (the build container has every development
package installed, so a library that should have been bundled would
otherwise pass unnoticed there):

- glibc: `libc`, `libm`, `libresolv` and the dynamic loader
- `libgcc_s`, `libstdc++`
- `libwayland-client`, `libX11`, `libxcb`
- `libfontconfig`, `libfreetype`, `libharfbuzz`, `libfribidi`
- `libz`, `libgmp`, `libgpg-error`, `libcom_err`

Why the compiler runtime and the display libraries come from the host, and
not from Ubuntu 24.04, was measured against a current host (CachyOS, Mesa
26.2, Wayland 1.26, GCC 16), not assumed. The host's GPU driver is loaded
into the same process and needs these libraries in versions at least as new
as its own, and a process holds only one copy of each:

- `libwayland-client`: the host's Mesa EGL and Vulkan drivers use
  `wl_display_create_queue_with_name`, `wl_display_dispatch_queue_timeout`
  and `wl_fixes_interface`, which Ubuntu 24.04's 1.22 does not have. A
  bundled copy would keep the driver from loading on Wayland.
- `libstdc++`, `libgcc_s`: the host's Mesa and LLVM link them too. The
  bundled files need only `GLIBCXX_3.4.30` (GCC 12; ICU and LERC) and
  `GCC_4.2.0`, which every glibc 2.39 distribution exceeds.
- `libX11`, `libxcb`: the core X11 libraries the host's Mesa GLX / EGL use.

At run time, on Wayland and on X11, all of these were loaded from the host
while GTK drew with the host's Mesa (OpenGL by default; Vulkan, when forced,
worked too).

`libXau`, `libXdmcp`, `libbsd` and `libmd` are excluded as well: only the
host's `libxcb` needs them, it always loads its own, and the bundled copies
were never mapped.

#### Still bundled, kept under review

Measured working with the host's Mesa on Wayland and X11, to be confirmed on
other distributions:

| Library | Decision | Measured |
|---|---|---|
| `libwayland-egl.so.1` | bundle | Needs only glibc; GTK links it. Loaded from the AppDir on Wayland, with the host's Mesa 26.2 drawing through it |
| `libvulkan.so.1` (the Vulkan loader, not a driver) | bundle | GTK links it, so it must resolve; GTK 4.14 draws with OpenGL by default and loaded no Vulkan driver. With `GSK_RENDERER=vulkan` (diagnosis only) the bundled loader used the host's driver and worked |
| X extensions: `libXext`, `libXi`, `libXfixes`, `libXrandr`, `libXinerama`, `libXcursor`, `libXdamage`, `libXrender`, `libxcb-render`, `libxcb-shm` | bundle, to be confirmed | GTK and cairo link them. The host's Mesa also uses the bundled `libXext` and `libxcb-shm` (all the symbols it needs are there); confirm on other distributions' X11 sessions |

#### Host requirements

Beyond the libraries above, the host must provide:

- glibc 2.39 or later
- the D-Bus system and session buses, UDisks2, polkit and a polkit
  authentication agent (as for every build of the app)
- `shared-mime-info` (`/usr/share/mime`): gdk-pixbuf recognises SVG icons
  through it; without it, SVG icons fail to load
- preferably `xdg-desktop-portal` with a file chooser: GTK uses the
  desktop's file dialog through it, and its own otherwise (which works too,
  with the bundled schema)
- fonts for the language the app is shown in -- for Japanese, a font with
  CJK coverage (e.g. Noto Sans CJK). The AppImage bundles no fonts and uses
  the host's (fontconfig). Measured on the openSUSE Tumbleweed GNOME live
  system, which has no Japanese font: the Japanese translation was loaded
  and laid out, but every Japanese character was drawn as a missing-glyph
  box

#### Running from removable media

On removable media such as FAT-formatted USB drives, the desktop's mount
options can keep an AppImage from being executed directly. Measured on KDE
Plasma (step 7.2): UDisks2 mounted a vfat USB drive with `showexec`, which
gives the execute permission only to `.exe`, `.com` and `.bat` files, so the
`.AppImage` could not be made executable there (a mount option such as
`fmask=0022` did not change that). Other filesystems and mount settings may
allow it. In that case, copy the AppImage to the home directory,
`~/Downloads`, or another local filesystem that allows execution, and run it
from there.

#### The app's style on GTK 4.14

The app's own look (`src/bin/linux-image-writer/style.css` and
`style-dark.css`) is written with libadwaita's named colours
(`@define-color`, `@accent_color`, `alpha()`), which GTK 4.14 /
libadwaita 1.5 and every later version understand, so the AppImage shows the
same yellow accent and slate palette as the Flatpak, with no CSS warnings.
Earlier versions used CSS custom properties, `var()` and `color-mix()`
(GTK 4.16 and later only), which Ubuntu 24.04's GTK rejected. Keep the
stylesheets to GTK 4.14's CSS when changing them; a "Theme parser error" at
the AppDir's start-up means they are not.

#### Known issues

- GTK's and libadwaita's own texts (e.g. in GTK's file dialog) are
  translated with the host's catalogs, when the host has them.
- **`--appimage-extract-and-run` leaves its extraction behind.** The type 2
  runtime extracts the AppImage to `$TMPDIR/appimage_extracted_<md5>` (about
  95 MB) and, by its source, should delete it when the app exits; on the test
  host it stays -- with the pinned and the newest runtime alike, in `/tmp` or
  elsewhere, and for a minimal AppImage too, so it is the runtime's
  behaviour, not this AppImage's. The normal (FUSE) start leaves nothing.
  Not yet reported upstream.

### No added privileges

The AppImage adds none of the following, and must never need them:

- Running as root, or a `sudo` / `pkexec` wrapper
- udev rules
- polkit policy changes
- Direct permissions on USB devices

The app's least-privilege design (it holds a device only through the file
descriptor UDisks2's `OpenDevice` returns, after the host's polkit allows it)
is the same in the AppImage as everywhere else.

### Wayland and X11 are not forced

The AppImage does not set `GDK_BACKEND`, or any other variable that selects a
display backend or renderer. GTK picks Wayland or X11 as it normally does.
The launcher (`AppRun`) sets only the few variables needed for GTK to find
the resources inside the AppImage, and no `LD_LIBRARY_PATH`.

### Pinned tools

`linuxdeploy`, `appimagetool` and the AppImage type 2 runtime are downloaded
at fixed, tagged releases and checked against the SHA-256 sums in
`tools.lock` (which GitHub's published digests confirm) on every use. Moving
"continuous" builds are not used. The runtime is pinned on its own and given
to appimagetool with `--runtime-file`, so appimagetool never fetches one; it
is the static FUSE 3 runtime, so the host needs no `libfuse2`.

### Generated files are not in Git

The AppDir and the AppImage are build outputs. They are recreated by every
build and are never committed.

### No destructive USB tests in the early stages

Building the AppImage does not involve any USB device. In the early stages,
the AppImage is tested only up to the final confirmation before writing
(which is then cancelled): start-up, display, Japanese UI, Wayland, X11,
choosing an image, listing USB drives through UDisks2, the safety checks, and
exiting. Writing to a real USB drive was verified for v0.1.0; if a check of
the AppImage is needed, a single minimal write is done later, by hand.

## AppRun

`AppRun` (POSIX sh) finds the AppDir (`$APPDIR`, set by the AppImage runtime,
or its own location), sets five variables, and runs
`exec "$APPDIR/usr/bin/linux-image-writer" "$@"`:

| Variable | Value | Why |
|---|---|---|
| `XDG_DATA_DIRS` | `$APPDIR/usr/share` first, then the host's (or the XDG default) | The bundled icons and schemas; the host's data stays visible |
| `GSETTINGS_SCHEMA_DIR` | `$APPDIR/usr/share/glib-2.0/schemas` | GTK's file chooser schema. Measured: with no file chooser portal and no GTK 4 on the host, GTK's own file dialog aborts the app without it |
| `GIO_MODULE_DIR` | `$APPDIR/usr/lib/gio/modules` (empty) | The bundled GLib never loads the host's GIO modules, built for another GLib. Measured: no effect on warnings, the file dialogs, D-Bus / UDisks2, or light/dark switching (through the portal); GTK's own file dialog just does not remember its view settings |
| `GDK_PIXBUF_MODULE_FILE` | `$APPDIR/usr/lib/gdk-pixbuf-2.0/2.10.0/loaders.cache` | The bundled SVG loader (below) |
| `GTK_EXE_PREFIX` | `$APPDIR/usr` exactly | The bundled GTK loads **no host GTK modules** (below). Not for themes or GTK's data |

It sets nothing else: no `LD_LIBRARY_PATH` or `LD_PRELOAD` (libraries are
found through RUNPATH), no `GDK_BACKEND`, `GSK_RENDERER`, `GTK_THEME`,
`GTK_PATH` or `GTK_DATA_PREFIX`, and no D-Bus addresses. It never elevates
privileges. `check-appdir.sh` enforces all of this, and that
`GTK_EXE_PREFIX` is set, exported, once, to exactly `"$APPDIR/usr"`.

### GTK modules: none, neither bundled nor the host's

GTK loads dynamic modules at run time -- input methods (`immodules`), media
backends (`media`), print backends (`printbackends`) and the inspector --
from `<prefix>/lib/gtk-4.0`, where `<prefix>` is `GTK_EXE_PREFIX` if set
and otherwise the library directory GTK was built for (GTK 4.14's
`gtk/gtkmodules.c`: `GTK_EXE_PREFIX` is used for this and nothing else).
The bundled GTK was built for `/usr/lib/x86_64-linux-gnu`, which is also
where Debian and Ubuntu install **their** GTK's modules, built for their GTK
and GLib. The VM tests measured, without `GTK_EXE_PREFIX`:

- Debian 13 (GTK 4.18, GLib 2.84): the host's ibus and fcitx5 input method
  modules were loaded into the app, and its GStreamer media module failed on
  every start (`undefined symbol: g_sort_array`, a GLib 2.82 function the
  bundled GLib 2.80 lacks; `Failed to load module: …/libmedia-gstreamer.so`);
- Ubuntu 24.04 (the same GTK): the ibus module and the GStreamer media
  module with the whole GStreamer stack were loaded;
- Fedora and openSUSE: nothing (their modules are under `/usr/lib64`).

`GTK_EXE_PREFIX="$APPDIR/usr"` points GTK at `$APPDIR/usr/lib/gtk-4.0`,
which the AppImage does not have (`check-appdir.sh` fails if it does), so
no module is loaded, from anywhere. `GTK_PATH` (which would add directories
to the search) stays unset.

What the app loses by it, checked against its source:

- **Input methods.** Linux Image Writer v0.1.x has no text entry of its own
  (no `GtkEntry`, `GtkText`, `GtkTextView`, `GtkSpinButton`, search or
  editable label, nor libadwaita entry rows), so it needs no input method:
  **no effect on its function**. The only text fields it can show are
  GTK's own file dialog's location and search fields, and only when no
  file chooser portal is available; there, without the host's IBus / Fcitx
  module, typing is plain (no IME composition, e.g. for Japanese file names)
  on X11 (measured: typing into the dialog's search field works). When the
  session sets `GTK_IM_MODULE` (Debian Xfce: `ibus`), opening that dialog
  prints one harmless `Gtk-WARNING: No IM module matching GTK_IM_MODULE=ibus
  found`. On Wayland, GTK's built-in text-input support is used regardless,
  and the portal file dialogs run in their own process.
  **TODO:** if a text entry is ever added to the app, revisit the AppImage's
  input method policy (bundling IBus / Fcitx modules built for the bundled
  GTK, or another approach) before release.
- **Media and printing.** The app uses no `GtkMediaFile` / `GtkMediaStream`
  / `GtkVideo` and no printing, so nothing is lost.
- The app starts no other programs, so `GTK_EXE_PREFIX` reaches no other
  process (the portals are D-Bus services, started by D-Bus).

## GTK runtime resources

Added only where a measurement showed GTK needs them:

- **GSettings schema**: only `org.gtk.gtk4.Settings.FileChooser` (from
  `libgtk-4-common`), compiled with `glib-compile-schemas`. Nothing else
  asks for a schema.
- **gdk-pixbuf SVG loader** (`libpixbufloader-svg.so` and `librsvg`, from
  `librsvg2-common` / `librsvg2-2`). Without it, GTK skips every SVG icon:
  libadwaita 1.5 embeds its own icons (such as the expander arrow) only as
  SVG, and they showed as "missing image"; theme icons fell back to unrelated
  colour ones. Its cache names the loader without a directory
  (`"libpixbufloader-svg.so"`), so gdk-pixbuf opens it through libgmodule's
  RUNPATH (`usr/lib`) wherever the AppImage is mounted: nothing is written at
  run time.
- **Icons** (`icons.txt`): of the 15 symbolic icons the GUI names, 10 are
  embedded in GTK or libadwaita; the other 5 are copied from Ubuntu's
  Adwaita theme into `usr/share/icons/hicolor/scalable/`, with hicolor's
  `index.theme`. With the host's icon themes hidden (diagnosis), every icon
  still showed. The icon theme is never bundled as a whole.
- **No GIO modules**, no input method, print or media modules (the GUI has no
  text entry, printing or video).

## Licences

Every bundled Ubuntu package's licence statement is in the AppImage, exactly
as the package installed it, and checked on every build:

- `build.sh` (`add_license_documents`) finds the package of every library in
  `usr/lib` (by name, so packages that register their files under `/lib`
  rather than `/usr/lib` are found too) and of every resource file, and
  copies each package's `/usr/share/doc/<package>/copyright` into the AppDir.
  linuxdeploy's own copying is turned off: it missed `liblzo2-2`, which
  still registers its library as `/lib/x86_64-linux-gnu/…`, because it asks
  dpkg about the `/usr/lib/…` path.
- Most Debian copyright files give a licence's full text only by reference to
  `/usr/share/common-licenses/<name>`, which hosts other than Debian's lack;
  the texts referred to (GPL-2, LGPL-2.1, Apache-2.0, …) are copied from
  `base-files` into `usr/share/common-licenses/`, with `base-files`' own
  copyright file.
- The app's own licence: `LICENSE` (GPL-3.0-or-later) as
  `usr/share/doc/linux-image-writer/LICENSE`.
- The licences of the Rust crates compiled into the binary (statically, as
  Rust does): the repository's `data/THIRD-PARTY-LICENSES.txt`, installed as
  `usr/share/doc/linux-image-writer/THIRD-PARTY-LICENSES.txt` (the Flatpak
  ships the same file). It is generated from `Cargo.lock` by the pinned
  cargo-about and checked against Cargo's own dependency graph and the
  binary by `build-aux/rust-licenses/generate.sh` (its README has the
  details). The build regenerates it first and **stops unless the
  committed copy is byte for byte the generated one** (a stale copy must be
  regenerated and committed). Named apart from the Ubuntu packages'
  `copyright` files; it covers the crates only, and says so.
- Nothing is written by hand: the Ubuntu packages and the crates are the
  source of truth.

`check-appdir.sh` fails the build if a bundled package has no copyright file
or one that differs from the package's, if a referred-to licence text is
missing or differs, if a licence document belongs to no bundled package, or
if the app's `LICENSE` is missing or differs, or if `THIRD-PARTY-LICENSES.txt`
is missing, differs from `data/THIRD-PARTY-LICENSES.txt`, or is not the
document `generate.sh` checked (its SHA-256 is compared with the one
`out/rust-license-manifest.txt` records). It writes
`out/license-manifest.txt`: for each package, its version, source package,
the licences its copyright file names (when machine-readable), the document
and its SHA-256, and the bundled files it covers; then the common licence
texts, the app's own licence and the Rust crates' document (with the
SHA-256 of `rust-license-manifest.txt`, which lists every crate).

## Corresponding source

Every bundled package whose licence asks for its source to be available is
carried as source next to the AppImage, from the same place: the release
gets `LinuxImageWriter-<version>-appimage-sources.tar.zst` beside the
AppImage. Links to the Ubuntu snapshot are given for provenance only.

- **Which packages.** `check-appdir.sh` classifies each bundled package's
  licences with `license-review.txt` and writes the classes and a
  `source-required` column into `out/license-manifest.txt`. A package needs
  its source carried when any of its licences is copyleft (GPL, LGPL, MPL,
  GFDL, CC-BY-SA) -- also when it is only one alternative -- or not reviewed:
  on the safe side. `license-review.txt` maps every licence name the
  machine-readable copyright files use to a class, and records, by SHA-256,
  the review of each copyright file that is not machine-readable; an unknown
  name, an unreviewed file or a file changed since its review fails the
  build.
- **Which source.** `sources.sh` (in the build container, after `build.sh`)
  takes the source package and version each of those binary packages was
  built from, and fetches exactly that version from the same Ubuntu snapshot
  (`apt-get source`, the snapshot's `deb-src` index enabled in the container
  only). The `.dsc` must match the snapshot's signed Sources index, and every
  file it lists must match its SHA-256; downloads are kept in
  `out/source-cache/` and verified again on every use. Each source package
  shared by several binary packages is fetched once.
- **The archive.** `out/sources/<source package>/` holds each source
  package as Ubuntu publishes it (`.dsc`, `.orig.tar.*`, `.debian.tar.*`),
  with `out/sources/source-manifest.txt` (for each source package: version,
  the bundled binary packages, licence classes, bundled files; every file's
  SHA-256; the snapshot URL it came from). It is packed reproducibly (sorted,
  fixed times and owners, `zstd -19`) into
  `out/dist/LinuxImageWriter-<version>-appimage-sources.tar.zst` with its
  `.sha256`, then extracted and checked: no file missing or extra, every
  checksum right, every `.dsc` and version the needed one.
  `sources.sh --check <archive>` checks an existing archive the same way.

```sh
podman run --rm --security-opt label=disable -v "$PWD":/src \
  linux-image-writer-appimage-build build-aux/appimage/sources.sh
```

The app's own source (GPL-3.0-or-later) is this repository; how a release
provides it is decided with the release process.

| `exclude-libs.txt` | Libraries never bundled, with reasons (and those kept under review, not enforced) |
| `host-libs.txt` | The only libraries that may come from the host |
| `icons.txt` | Every icon the GUI names, and where the AppImage gets it |
| `license-review.txt` | How each licence name, and each copyright file that is not machine-readable, is classified |
| `sources.sh` | The third-party source archive (see "Corresponding source") |
| `tools.lock` | Pinned external tools: release, URL and SHA-256 |
| `../rust-licenses/` | The Rust crates' licence document, shared with other packagings: cargo-about's pin, configuration and template, and its checks |
| `out/` | Build output, not in Git: the AppDir, `bundle-manifest.txt`, `license-manifest.txt`, `rust-license-manifest.txt`, `THIRD-PARTY-LICENSES.txt`, `linuxdeploy.log`, `appimagetool.log`, the AppImage, the source archive and their SHA-256 in `out/dist/`, the source tree in `out/sources/`, downloaded tools in `out/tools/` and source packages in `out/source-cache/` |


## The AppDir

`build.sh` produces `out/LinuxImageWriter.AppDir`: the binary, the app's own
files, each installed from its source of truth (no copies are kept in the
repository), the libraries linuxdeploy collects, GTK's runtime resources and
`AppRun`:

```
LinuxImageWriter.AppDir/
├── AppRun                                           build-aux/appimage/AppRun
├── io.github.pc_freedom.linux-image-writer.desktop  -> usr/share/applications/…
├── io.github.pc_freedom.linux-image-writer.svg      -> usr/share/icons/hicolor/scalable/apps/…
├── .DirIcon                                         256x256 PNG rendered from the SVG (rsvg-convert)
└── usr/
    ├── bin/linux-image-writer                       target/appimage/release (built in the container)
    ├── lib/                                         libraries and the SVG loader (linuxdeploy), RUNPATH $ORIGIN
    │   ├── gdk-pixbuf-2.0/2.10.0/loaders.cache      generated (SVG loader only)
    │   └── gio/modules/                             empty
    └── share/
        ├── applications/…desktop                    data/
        ├── metainfo/…metainfo.xml                   data/
        ├── glib-2.0/schemas/                        GTK's FileChooser schema, compiled
        ├── icons/hicolor/scalable/apps/…svg         data/icons/
        ├── icons/hicolor/scalable/<context>/        5 symbolic icons from Adwaita, with hicolor's index.theme
        ├── locale/<lang>/LC_MESSAGES/linux-image-writer.mo
        │                                            po/<lang>.po, for each language in po/LINGUAS
        ├── doc/<package>/copyright                  every bundled package's copyright file (see "Licences")
        ├── doc/linux-image-writer/LICENSE           LICENSE
        ├── doc/linux-image-writer/THIRD-PARTY-LICENSES.txt
        │                                            data/ (the Rust crates' licences, from build-aux/rust-licenses)
        └── common-licenses/                         the licence texts those copyright files refer to
```

Run it directly with `out/LinuxImageWriter.AppDir/AppRun` (on the host, not in
the container).

`build.sh` runs these stages:

1. **Environment check.** It refuses to run outside a container or on
   anything but Ubuntu 24.04, so the host's own toolchain and libraries can
   never end up in the AppImage.
2. **Clean output.** The previous AppDir, manifest and log are removed first.
3. **Icon list.** Every `"…-symbolic"` icon name in the GUI's source must be
   in `icons.txt`, and `icons.txt` must list nothing else.
4. **Binary.** `cargo build --release --locked --features gui --bin
   linux-image-writer`, always into `target/appimage` (never the host's
   `target/release`). Tests are not run here; run `cargo test` separately.
   Then **the Rust crates' licence document**: regenerated
   (`build-aux/rust-licenses/generate.sh --check`, given the binary) and
   compared with `data/THIRD-PARTY-LICENSES.txt`, which is what the AppImage
   ships; the build stops if they differ. The generated copy and its
   manifest are kept under temporary names until the AppDir is complete.
5. **Assembly**, under a temporary name. Translations are compiled as the
   Flatpak manifest does, with `msgfmt --check`.
6. **Checks on the app's files.** The binary must be identical to cargo's and
   linked by Ubuntu 24.04's toolchain; every other file is compared byte for
   byte (`cmp`) with its source; each `.mo` must be a GNU message catalog;
   `desktop-file-validate` and `appstreamcli validate` must pass.
7. **linuxdeploy**, at the release `tools.lock` pins, verified by SHA-256 on
   every use, run with every pattern from `exclude-libs.txt` and the SVG
   loader as an extra library. It copies the libraries into `usr/lib` and
   sets `RUNPATH` (`$ORIGIN/../lib` on the binary, `$ORIGIN` on the
   libraries); it does not strip the binary. It also links `AppRun` to the
   binary, which `build.sh` removes. Its log is `out/linuxdeploy.log`.
8. **GTK resources**, **AppRun** (above) and **licence documents** (see
   "Licences").
9. **Checks on the app's files, again**, so linuxdeploy cannot have changed
   them, and **checks on the AppDir** (`check-appdir.sh`, below).
10. **Finish.** Only then is the AppDir renamed to its final name, the
    manifests moved to `out/bundle-manifest.txt`, `out/license-manifest.txt`
    and `out/rust-license-manifest.txt` (with `out/THIRD-PARTY-LICENSES.txt`),
    and the contents listed.
11. **AppImage** (see "The AppImage").

Any failure stops the build with a non-zero exit status and leaves no AppDir
(or, once the AppDir is complete, no AppImage).

### Checks on the bundle

`check-appdir.sh APPDIR MANIFEST` examines every ELF file and fails, naming
each file at fault, if the AppDir contains:

- a library matching `exclude-libs.txt` (by file name or SONAME)
- a file from a package that is never bundled (glibc, Mesa and GPU drivers,
  libglvnd, libdrm, UDisks2, D-Bus, polkit, kernel images and modules)
- a GPU driver module (`dri/`, `*_dri.so`, Vulkan ICDs, ...), a kernel
  module, or a daemon (`udisksd`, `dbus-daemon`, `polkitd`, ...)
- an executable other than `usr/bin/linux-image-writer`, or an interpreter
  other than `/lib64/ld-linux-x86-64.so.2`
- a dependency that does not resolve, a glibc symbol version newer than 2.39
  (or `GLIBC_PRIVATE`), or a `RUNPATH` / `RPATH` not relative to `$ORIGIN`
- a dependency resolved outside the AppDir that `host-libs.txt` does not
  allow
- an `AppRun` that is missing, a symbolic link, sets one of the variables
  listed under "AppRun" as never set, calls a privilege tool, or does not end
  by running the binary; or that does not set and export `GTK_EXE_PREFIX`,
  once, to exactly `"$APPDIR/usr"` before running it (missing, a host path
  such as `/usr`, or any other value fails, naming the value)
- any GTK module (`usr/lib/gtk-4.0`)
- a GSettings schema that is not GTK's own, or no compiled schemas
- any GIO module; a gdk-pixbuf loader other than the SVG loader; a loader
  cache that names a loader by path or one not in `usr/lib`
- an icon `icons.txt` does not account for, an icon it copies that is
  missing, or one it says GTK / libadwaita embed that they do not
- a `.DirIcon` that is missing, a link, or not a 256x256 PNG
- a bundled package without its copyright file, or a licence document or
  text that is missing, altered or unaccounted for (see "Licences")
- no `THIRD-PARTY-LICENSES.txt`, or one that differs from
  `data/THIRD-PARTY-LICENSES.txt` or from the document `generate.sh` checked

The manifest records, without timestamps or absolute paths, so that two
builds can be compared with `diff`:

- the inputs (Ubuntu release, snapshot ID, linuxdeploy release and SHA-256)
- every ELF file: SONAME, Ubuntu package and version, the file it came from,
  newest glibc version, RUNPATH, and each NEEDED library with whether it
  resolves inside the AppDir or on the host
- the libraries left to the host, the newest symbol version needed from each,
  and which files need them; and any `host-libs.txt` entry no longer needed
- where every other file comes from (this repository, a generated file, or
  an Ubuntu package and version)
- for every ELF file, the glibc symbols at its newest version
- every file's SHA-256, size and mode, and every symbolic link

Two builds from the same inputs produce identical manifests, including the
binary's SHA-256 after a clean cargo build.

## The AppImage

`build.sh` packs the finished AppDir with appimagetool and the pinned type 2
runtime into `out/dist/LinuxImageWriter-<version>-x86_64.AppImage`, then
writes `<file>.sha256` beside it (`<hash>  <file>`, for `sha256sum -c`).

- **Test builds by default.** `<version>` is `<Cargo version>-test` unless
  `APPIMAGE_VERSION` is set, so a build is never mistaken for a release. A
  release build sets it explicitly (the release process is still to be
  written).
- **Reproducible.** Every file in the squashfs gets the same time and root
  ownership (`-all-time`, `-mkfs-time`, `-all-root`): the time is
  `SOURCE_DATE_EPOCH` if set, else the Ubuntu snapshot's. Two builds from the
  same inputs give byte-identical AppImages.
- **`.DirIcon`** is a 256x256 PNG rendered from the SVG icon at build time:
  the AppImage specification requires a `.DirIcon` and says it SHOULD be a
  256x256 PNG, and integration tools read it as an image (KDE's AppImage
  thumbnailer, through libappimage and Qt, which reads PNG itself but SVG
  only with an optional plugin). appimagetool accepts either. The SVG stays
  the only source; no PNG is kept in the repository.
- **MetaInfo.** appimagetool runs with `--no-appstream`: it looks only for
  the old `<id>.appdata.xml` name, while the MetaInfo is
  `<id>.metainfo.xml` and is validated with `appstreamcli` by `build.sh`.
- **Not signed** and **no update information** yet.

Checks on the AppImage (`check_appimage`), before it gets its name:

- an executable, type 2 AppImage (magic `AI\x02`)
- its runtime is the pinned one: same size, and the same bytes except the
  sections appimagetool fills in (update information, signature, digest)
- extracted (`--appimage-extract`), its contents are identical to the AppDir
  (files, modes, links), pass `check-appdir.sh`, and give the same bundle
  manifest

Run it with `out/dist/LinuxImageWriter-<version>-x86_64.AppImage`, or, where
FUSE is not available, with `--appimage-extract-and-run` (see "Known
issues").

## Using the build environment

Requirements on the host: Podman (rootless is enough) or Docker. Nothing
else is installed on the host.

Build the container image, from the repository root:

```sh
podman build -t linux-image-writer-appimage-build \
  -f build-aux/appimage/Containerfile .
```

Build the AppDir and the AppImage inside it, with the repository mounted at
`/src`:

```sh
podman run --rm \
  --security-opt label=disable \
  -v "$PWD":/src \
  -v linux-image-writer-cargo-registry:/opt/cargo/registry \
  linux-image-writer-appimage-build \
  build-aux/appimage/build.sh
```

Or build and test only the GUI:

```sh
podman run --rm \
  --security-opt label=disable \
  -v "$PWD":/src \
  -v linux-image-writer-cargo-registry:/opt/cargo/registry \
  -e CARGO_TARGET_DIR=/src/target/appimage \
  linux-image-writer-appimage-build \
  cargo build --release --locked --features gui --bin linux-image-writer
```

(The same command with `cargo test --locked --features gui` runs the tests.)

- The image has no default Rust toolchain: the version is chosen by the
  repository's `rust-toolchain.toml`, so cargo must run inside `/src`.
- `CARGO_TARGET_DIR=/src/target/appimage` keeps the container's build apart
  from the host's own `target/release`, which is built against a different
  glibc and GTK.
- The named volume keeps downloaded crates between runs.
- With rootless Podman, files the container writes are owned by your user.
- `--security-opt label=disable` avoids relabelling the repository on
  SELinux hosts.
